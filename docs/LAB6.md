## Lesson 6.1: Structured discovery and requirement gathering

**The idea**
- Stakeholders state a WANT in solution language ("an AI that reads loan documents"). Discovery finds the
  NEED: What happens today without this? What does success look like in six months? Who is hurt, and how?
- A REQUIREMENT is an outcome the system must deliver, checkable once built. A CONSTRAINT limits how
  (budget, platform, regulation, skills).
- The binding test: "what happens if this can't be met?" "We'd revisit the whole approach" means binding;
  "we'd prefer it but could work around it" means a preference. Integrating with the loan-origination
  platform is binding; showing results in the Lending Hub dashboard is a preference.
- Write it down as an artifact, and validate it WITH the stakeholder. Silence is not agreement.

**Practical:** `atlas/requirements.py`: `classify_constraint()`, then `NEED_STATEMENT`, `REQUIREMENTS`
(each with a metric and a target) and `CONSTRAINTS` (binding or not, with the owner's answer as the
reason) from `docs/discovery_notes.md`.

**Check:** `pytest tests/test_lab6.py -k test_6_1`

## Lesson 6.2: Communicating architectural decisions and trade-offs

**The idea**
- Same decision, two audiences. Engineers want the mechanism: what, why, the rejected alternative.
  Executives want consequences: cost, risk and timeline against the business outcome. Translating means
  choosing which true facts each audience needs, not losing substance.
- Name every trade-off honestly: what it buys, what it gives up, why that is acceptable. A cost that
  surfaces later undisclosed is a communication failure.
- Route feedback: a missed requirement changes the design; discomfort with a tested binding constraint
  gets a clear explanation, not a quiet concession to the loudest voice.
- An SLA is measurable ("95% of case files within 60 seconds"), never "fast and reliable". Quality targets
  are reported per category.

**Practical**
1. `atlas/communication.py`: `is_measurable()`, `lint_decision()`, `route_feedback()` and
   `summarize_for()` (one status, two framings; the executive one has no jargon).
2. `docs/decisions/ADR-001-investigator-tier.md`: write the decision record for "the investigator runs on
   the most capable tier, intake on the compact one". Use your Lab 4 numbers. Template:
   `docs/decisions/adr_template.md`.

**Check:** `pytest tests/test_lab6.py -k test_6_2`

## Lesson 6.3: Documentation, handoff and the solution life cycle

**The idea**
- Five phases: discovery (the requirements artifact), design (decisions AND the reasoning), handoff (a
  package a team can run without the architect), monitoring (signals and thresholds), iteration (update
  every earlier artifact a change affects). Documentation is a thread from phase one, consolidated at
  handoff, not written from memory at the end.
- The test: could someone who was never in the room run it correctly from what is written? Document WHY:
  a tier with no recorded reason gets downgraded in a cost review, and the accuracy problem returns.
- Operational guidance: for each signal, what it means and the correct response; for each of the four
  escalation triggers, which queue and role; an authorization failure during an outage is a DENIAL to
  investigate, not a bug to route around.
- Stale docs are worse than none (they are trusted). Give each document an owner and an update trigger
  tied to the event that changes the system.

**Practical**
1. `docs/RUNBOOK.md`: alerts (every id in `monitoring.ALERTS`), triggers with the queue and role from
   `escalation.QUEUES`, failure modes that are correct behaviour, routine operations.
2. `docs/HANDOFF.md`: owner, update trigger, the need, every requirement and constraint id, measurable
   service levels, the architecture with the WHY per component, the life-cycle table.

**Check:** `pytest tests/test_lab6.py -k test_6_3`. If you later add an alert or change a queue, these
tests fail until the runbook is updated: documentation kept current by design.
